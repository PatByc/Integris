## DEC-001: Stack selection

Date: 2026-05-09
Status: accepted

Decision: Next.js 15 + TypeScript + Tailwind (frontend), FastAPI + Python 3.12 + SQLAlchemy async + Alembic (backend), Supabase (Postgres + Auth + Storage), Redis + Python workers (queue), Google Cloud Vision (OCR), OpenAI gpt-4.1-mini (AI extraction).

Reason: Supabase provides managed Postgres, Auth (JWT), and Storage in one service, eliminating separate infra. FastAPI async fits the I/O-heavy worker pattern. Next.js App Router enables SSR for initial document list without a separate BFF.

Tradeoffs: Supabase SDK is sync in Python; httpx used directly for async storage uploads. SQLAlchemy async requires asyncpg driver; migrations via Alembic rather than Supabase migrations.

Follow-up: shadcn/ui was planned but dropped — Tailwind utility classes used directly throughout.

## DEC-002: AI must never generate FA(3) XML directly

Date: 2026-05-09
Status: accepted

Decision: AI (LLM) is used only for OCR-text → structured JSON extraction. FA(3) XML is generated by a deterministic Python function (`workers/fa3_xml.py`) after human approval.

Reason: KSeF FA(3) XML must be schema-correct and legally binding. LLM output is non-deterministic and cannot be trusted as a source of truth. Any error in submitted XML can result in invoice rejection or compliance issues.

Tradeoffs: More pipeline stages (extract → validate → review → XML generate). But correctness and auditability are non-negotiable.

Follow-up: `generate_fa3_xml()` must be tested for determinism and schema conformance on every change.

## DEC-003: Multi-tenant isolation via company_id on every query

Date: 2026-05-09
Status: accepted

Decision: Every document query includes `company_id` from the caller's membership. Cross-company access returns 404, not 403.

Reason: 403 leaks the fact that a document exists. 404 is correct — from the caller's perspective, a document in another company simply does not exist.

Tradeoffs: Slightly obscures permission errors during debugging. Accepted as the correct security posture.

Follow-up: Verified by `tests/test_api.py` multi-tenant tests.

## DEC-004: Validation logic lives in workers, mirrored in backend service

Date: 2026-05-09
Status: accepted

Decision: Deterministic validation rules are implemented twice — `workers/validation.py` (dict-based, used by background validation worker) and `backend/app/services/invoice_validation_service.py` (ORM model-based, used after user edits in review UI). Both implement identical rules.

Reason: The workers run in a separate process with no ORM access; they use raw psycopg2 dicts. The backend service uses SQLAlchemy ORM models. Sharing a single implementation would require coupling the two environments.

Tradeoffs: Rules must be kept in sync manually. Mitigated by unit tests covering the dict-based version (which is the worker path).

Follow-up: If rules diverge, the worker version (tested) is authoritative.

## DEC-005: Alembic for DB migrations, not Supabase migrations UI

Date: 2026-05-09
Status: accepted

Decision: All schema changes go through Alembic (`backend/alembic/versions/`). Supabase is used only as a managed Postgres host.

## DEC-006: Redis job queue with Python workers (no managed queue)

Date: 2026-05-09
Status: accepted

Decision: Background jobs (OCR, extraction, XML generation, KSeF submission, UPO polling) use Redis lpush/brpop via a thin wrapper in `workers/queue.py`. No SQS, Celery, or RQ.

Reason: Minimal operational complexity for MVP. Redis was already needed. Workers are simple polling loops (`BaseWorker`) with 3-retry exponential backoff.

Tradeoffs: No built-in dead-letter queue or visibility timeout. Retries tracked via `retry_count` on the document row. Acceptable for MVP scale.

Follow-up: 7 worker processes started by `scripts/start_dev.ps1`.

## DEC-008: PDF served via backend proxy, not signed Supabase URLs

Date: 2026-05-09
Status: accepted

Decision: The review UI fetches PDFs via `GET /api/v1/documents/{id}/pdf`, which streams the file from Supabase Storage after verifying company ownership. No signed URLs are exposed to the frontend.

Reason: Signed URLs bypass the company_id ownership check — any valid signed URL works regardless of tenant. Proxying through the backend keeps access control in one place.

Tradeoffs: Extra network hop through the backend for PDF bytes. Acceptable for MVP; PDFs are fetched once per review session.

Follow-up: Large PDFs (≤25 MB) stream as a single response. Streaming chunked transfer could be added later.

## DEC-009: Document status state machine (14 states)

Date: 2026-05-09
Status: accepted

Decision: Documents move through explicit statuses:
`uploaded → ocr_processing → ocr_failed (retryable)`
`→ extraction_processing → extraction_failed (retryable)`
`→ validation_failed → needs_review`
`→ needs_review → approved → xml_generated`
`→ submission_pending → submitted → accepted (terminal)`
`→ rejected (retryable via retry-submission)`
`→ cancelled (terminal)`

Reason: Explicit statuses make the pipeline observable, retryable at the right point, and auditable. Vague statuses like "processing" hide which stage failed.

Tradeoffs: State transitions must be enforced at the API level (422 for invalid transitions). Tested by `tests/test_api.py` state machine tests.

Follow-up: Status is indexed (`idx_documents_status_orm`) for dashboard filtering.

## DEC-010: Multilanguage support via next-intl (cookie-based, no URL routing)

Date: 2026-05-15
Status: accepted

Decision: `next-intl` with cookie-based locale (`NEXT_LOCALE` cookie, default `pl`). No `[locale]` URL segments — all routes stay as-is. Language toggle in Settings > System sets the cookie and calls `router.refresh()`. Translation files at `frontend/messages/pl.json` and `frontend/messages/en.json`, organised by namespace. Server components use `getTranslations()`, client components use `useTranslations()`.

Reason: Polish is the target market default. English is required for international users and the dev team. Cookie-based approach avoids restructuring all 15 app routes into `[locale]/` wrappers. Two languages only — no need for URL-based locale routing.

Tradeoffs: Locale not visible in the URL (not shareable by URL). Acceptable for a B2B SaaS app where users are always authenticated and locale is a personal preference. If URL-based locale is ever needed, migration to `[locale]/` routing is possible later.

Follow-up: Complete — `t()` wired in all 22 source files across 10 namespaces (Landing, Auth, Nav, Dashboard, Upload, DocumentsTable, StatusBadge, Review, Audit, Help, Settings). Avatar dropdown redesigned with `flex-row-reverse` so all menu texts are right-aligned and sub-menu chevrons appear on the left.

## DEC-015: Browser language auto-detection via Accept-Language header

Date: 2026-05-15
Status: accepted

Decision: `frontend/i18n/request.ts` now reads the `Accept-Language` request header when no `NEXT_LOCALE` cookie exists. If the header contains `"pl"`, locale defaults to Polish; otherwise English. If the header is absent entirely (bots, automated requests), defaults to Polish (target market).

Reason: First-time visitors always saw Polish regardless of browser language. English-speaking users or international team members had to manually switch in Settings before seeing English.

Tradeoffs: Detection runs on every request for visitors without the cookie (slightly more work per request). Once the user visits Settings or the cookie is set by any means, detection stops running.

Follow-up: None. The cookie remains the source of truth for returning visitors.

## DEC-019: Worker scaling — one shared queue per type, not per user

Date: 2026-05-16
Status: accepted

Decision: Workers are shared across all companies/users. One running OCR worker process handles all companies' jobs from the same Redis queue. Scaling is done by starting additional instances of the same worker type (they compete for jobs via `blpop`), not by running per-user or per-company workers.

Reason: The queue is company-agnostic; multi-tenant isolation is enforced at the data level (every job has `document_id` → worker fetches `company_id` from DB). Running separate workers per company would be operationally expensive and unnecessary.

Documented in `workers/base_worker.py` docstring.

Tradeoffs: None for MVP scale. At high load, a single slow company could delay others in the queue. Fair-queue scheduling is post-MVP.

Follow-up: If one company generates disproportionate volume, a per-company queue routing strategy can be added to `BaseWorker` without changing the worker logic.
